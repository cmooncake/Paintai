# Paintai 架构方案

> 一个会持续学习、持续进化的 AI 画师——模拟 AI 画师从零开始系统学画、持续成长的完整过程。
> 
> 方案版本：v1.1 | 2026-11-03  
> **本版变更**：① **课程路径可彻底自定义**——画师不再强制继承默认 6 阶段模板，每个画师实例携带自己的课程规格；② **画师可存档**——存档粒度支持 full（作品与记忆全打包，可迁移分享）与 pointer（只存配置与进度指针，作品留在原环境），导出时由一个 flag 切换。

---

## 一、核心概念

**实施补充（2026-11-03）**：已实现 CLI 和独立的 React + TypeScript 网页画室。前端通过 FastAPI `/api/v1` 调用业务层，后台持久化队列执行构思 / 生图 / 视觉评价；模型、凭据和作品存储留在后端。M1 已加入 Spec 驱动课程、三图过关、进度展示，以及按主题 / 技能检索的本地创作记忆基线。运行与接口见 [WEB.md](WEB.md) 和 [LEARNING.md](LEARNING.md)。M2a 已实现抽取式成对经验蒸馏和冻结经验成长对照，见 [GROWTH.md](GROWTH.md)。下文向量检索、完整 VED、成长泛化实验和存档仍是后续路线。

Paintai 不是又一个「输入 prompt 输出图片」的图像生成器。它的核心差异在于：

> **它不是一个生图工具，它是一个画画的 Agent——它有自己的学习轨迹、成长曲线、风格偏好和创作记忆。**

关键设计原则：

因此系统的一等公民不是「一次生图」，而是**画师实例（Painter Instance）**：一个实例 = 身份 + 配置 + 自己的课程规格 + 自己的记忆 + 自己的作品库。实例之间彼此隔离，可以并排存在、分别演进，也可以各自打包带走。

- **系统性学习**：不是一次性训练，而是分阶段的课程学习——从基础元素到高级风格、从模仿到创新
- **持续进化**：每次创作都是一次学习，失败和成功都会被内化为经验，下一次画得更好
- **可观测的成长**：你能看到它在不同阶段画同一主题的水平差异，就像看一个真实画家的进步
- **可自定义的课程**：画师不必走同一条学习路线。每个画师实例携带自己的课程规格（阶段列表 + 关卡），可以从零定义，也可以只借用内置模板——模板是默认值，不是约束
- **可存档的画师**：画师是「配置 + 课程 + 记忆 + 作品」的可打包实体，能导出、迁移、分享、派生。存档粒度可选：full（作品与记忆全打包，导入后独立运行）或 pointer（只存配置与进度指针，作品留在原环境）

上图为**单个画师实例**的内部结构。实例之上还有一层可打包的档案层——实例身份、课程规格、记忆与作品的归属关系；这一层决定了画师能否被导出、迁移与分享。

### 2.1 分层与存档边界

| 层次 | 内容 | 随实例隔离 | full 存档 | pointer 存档 |
|-|-|-|-|-|
| **实例档案层** | 身份、配置、课程规格、进度 | 是 | 打包带走 | 打包带走 |
| **记忆层** | 经验条目、蒸馏规则、风格偏好 | 是 | 打包带走 | 留在原环境（外部引用） |
| **作品层** | Gallery 图像、元数据、进化链 | 是 | 打包带走 | 留在原环境（外部引用） |
| **执行层** | Agent、Generator、Critic、Retriever | 否（共享代码与后端） | 不打包，按部署重装 | 不打包，按部署重装 |

「随实例隔离」是画师能被存档的前提：凡是随实例隔离的内容，都可以被完整打包或以指针形式引用；执行层是部署产物，不属于任何一个画师。

## 三、模块详解

### 3.1 Curriculum Engine（课程引擎）

AI 画师的「学习路线图」。画师不是随机学，而是按结构化课程逐步掌握绘画能力。课程引擎本身**不假设任何具体课程**——它只负责执行一份**课程规格（Curriculum Spec）**：规格里定义了什么阶段、什么关卡，画师就走什么路径。

**内置模板（default_curriculum）示例**——这是一个默认模板，不是所有画师必须走的路线：

| 阶段 | 名称 | 内容 | 预期输出 |
|-|-|-|-|
| L1 | 基础元素 | 线条、形状、色彩、明暗、纹理 | 基础元素练习稿 |
| L2 | 构图与空间 | 透视、比例、构图法则、正负空间 | 有构图的简单场景 |
| L3 | 技法入门 | 笔触模拟、色彩混合、材质表现 | 有技法意识的习作 |
| L4 | 风格临摹 | 学习经典风格（印象派、水墨、浮世绘等） | 风格临摹作品 |
| L5 | 主题创作 | 给定主题 + 技法 + 风格，综合创作 | 有明确风格指向的主题作品 |
| L6 | 自由创作 | 自主选题、融汇技法、追求表达 | 有个人印记的创作 |

**机制：**

- **阶段与关卡来自 Spec**：引擎只认 Spec 里的 stage / lesson 定义，不认 L1-L6 序号，也不假设阶段数为 6
- 每个阶段有若干关卡（Lesson），每个关卡有明确的训练目标
- 关卡完成后由 Critic 评估，通过则解锁下一关
- 画师可以在已完成阶段中反复练习（间隔重复强化记忆）
- **进度按稳定 ID 记录**：stage_id / lesson_id 是稳定标识符，Spec 改版或增删阶段不会让已有进度错位
- 学习进度、通过率、典型失败案例全部可追溯

**课程规格（Curriculum Spec）**——一份 Spec 就是一个画师的「出身」，可以与内置模板完全不同：

```yaml
painter_id: painter_wu
title: 水墨专项
stages:
  - id: ink_brush          # 稳定 ID，进度靠它对齐
    name: 笔墨基础
    goals: [线条控制, 墨分五色]
    lessons:
      - id: ink_brush_l1
        task: 画一组中锋线条
        pass_score: 6.5
        skills: [line_control]
  - id: ink_scene
    name: 写意场景
    lessons: [...]
progress:
  current_stage: ink_brush
  current_lesson: ink_brush_l1
  completed: [ink_brush_l1]
```

Spec 可以手写、从模板继承，或由 Agent 依据画师目标生成；引擎只做校验（阶段/关卡 id 唯一、依赖闭环、评分阈值合法、进度可对齐）与推进。自定义 Spec 与内置模板享有同等地位，**没有任何「必须继承 L1-L6」的硬约束**。

### 3.2 Painter Agent（画师核心）

这是系统的灵魂——一个 VLM-based（视觉语言模型）的 Agent，模拟画家的「感知 → 构思 → 执行」创作流程。

Agent 本身不持有状态——它运行在**某个画师实例的上下文**里：当前课程进度、风格库、历史作品与经验记忆都从该实例读取。因此同一份 Agent 实现可以驱动任意多个画师实例，它们互不污染。

#### 3.2.1 Perceive 感知模块

**职责**：理解输入——包括文字描述、参考图像、已有作品

- **文本理解**：解构主题描述，提取关键元素（主体、场景、情绪、约束）
- **图像理解**：分析参考图的构图、色彩方案、笔触特征、风格要素
- **自作品回顾**：从 Gallery 中检索自己的历史作品，理解当前能力和风格倾向

#### 3.2.2 Compose 构思模块

**职责**：在「画布」落笔之前，先在脑子里把画画完

- **参考检索**：根据主题从外部（web）和内部（Gallery）检索相关参考
- **风格匹配**：从当前已掌握的风格库中选择最合适的风格方向
- **构图规划**：确定画面布局、焦点、色彩方案、笔触策略
- **Prompt-Reference Program**：输出可执行的生图指令 `(gen_prompt, reference_images)`，借鉴 GenEvolve 的做法

#### 3.2.3 Execute 执行模块

**职责**：调用生图后端，把构思变成画面

- **生成器适配层**：支持多种生图后端（Stable Diffusion / DALL·E / Midjourney / ComfyUI workflow / Qwen-Image 等），可插拔
- **多轮修正**（Reflection）：生成后 Critic 评估 → 若不满意 → 修改 prompt/参考 → 重新生成，最多 N 轮
- **笔触级控制**（远期）：不只是 prompt-to-image，而是模拟真实笔触序列（参考 Stroke-GAN Painter）

---

### 3.3 Gallery（作品库）

AI 画师的作品档案。不是简单的图片文件夹，而是有结构、可检索的记忆系统。

**每条作品记录包含：**

- 作品图片
- 创作上下文（主题、阶段、课程、prompt、参考图）
- Critic 评分（多维度）
- 学习笔记（哪些做得好、哪些失败、为什么）
- 时间戳与版本链（同一主题的重画记录形成进化链）

**功能：**

- 支持语义检索（「我画过的日落的画」「水墨风格的作品」）
- 支持进化对比（同一主题在课程的不同阶段分别画成什么样）
- 支持风格一致性检查（新作品是否偏离了已建立的风格方向）

---

### 3.4 Critic（评价系统）

画师的「老师和自我批评能力」。没有评价就没有学习方向。

**多维度评分（每个维度 1–10）：**

| 维度 | 说明 |
|-|-|
| 主题契合度 | 是否准确表达了给定主题 |
| 技法完成度 | 当前阶段应有的技法是否到位 |
| 构图质量 | 布局、平衡、视觉引导 |
| 色彩和谐度 | 色彩搭配、氛围营造 |
| 风格一致性 | 与目标风格的匹配程度 |
| 创意表达 | 是否有超越模仿的原创表达（按当前阶段启用） |

**评价方式：**

- **规则评价**：可量化的指标（色彩直方图对比、构图规则检查等）
- **VLM 评价**：用视觉语言模型做主观审美判断 + 具体反馈文字
- **对比评价**：与其他画师（或自己的历史版本）对比打分
- **人类反馈（可选）**：对接外部评审接口

**输出**：评分 + 结构化的改进建议（不是「画得不好」，而是「红色区域饱和度过高，建议降低 15%，参考莫奈晚期的调色方式」）

---

### 3.5 Memory & Evolution Loop（经验记忆与进化循环）

这是「持续进化」的核心机制。

#### 3.5.1 Memory 结构

借鉴 GenEvolve 的 Visual Experience Distillation 思路，但为绘画场景重新设计：

**经验条目（Experience Entry）：**

```
{
  "id": "exp_042",
  "type": "success" | "failure" | "insight",
  "context": {
    "stage": "L4",
    "topic": "秋天的树林",
    "target_style": "印象派"
  },
  "trajectory": {
    "composition_plan": "...",
    "prompt": "...",
    "references": [...],
    "generations": [  # 多轮修正的记录
      {"round": 1, "image": "...", "critic_score": 6.2},
      {"round": 2, "image": "...", "critic_score": 7.8}
    ]
  },
  "distilled_lesson": {
    "what_worked": "用短笔触表现树叶颤动感，接近莫奈的破碎笔触",
    "what_failed": "远景树干过于清晰，破坏了空气透视",
    "rule": "L4+印象派风格：远景物体边缘模糊度应 > 0.7"
  }
}
```

**经验维度（5 个维度，借鉴 GenEvolve 框架）：**

1. **Search Strategy**：怎么找参考更有效
2. **Knowledge Activation**：当前主题该激活哪些已学技法
3. **Reference Selection**：选哪些参考图能最好地辅助创作
4. **Prompt Construction**：生图指令怎么写效果更好
5. **Failure Avoidance**：这次踩了什么坑，以后怎么避免

#### 3.5.2 Evolution Loop 进化循环

```
                    ┌──────────┐
                    │  Create  │  ← 根据当前能力 + 课程要求创作
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │ Evaluate │  ← Critic 多维度打分 + 生成改进建议
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │  Learn   │  ← 从成功/失败中提取经验，存入 Memory
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │  Evolve  │  ← 经验蒸馏 → 更新 Agent 策略 → 下一轮更强
                    └──────────┘
```

**进化策略（从简单到复杂，MVP 可选）：**

| 策略 | 说明 | 实现难度 |
|-|-|-|
| **Prompt 级自优化** | 基于历史经验自动调优 prompt 模板和参数 | ★★☆ |
| **Few-shot 经验注入** | 创作时从 Memory 检索相似场景的成功经验，注入上下文 | ★★☆ |
| **RAG 经验检索** | Memory 作为 RAG 知识库，创作时实时检索相关教训 | ★★★ |
| **LoRA 微调** | 积累一批高质量作品后，微调生成模型使其内化已学风格 | ★★★★ |
| **RL 策略优化** | 类似 GenAgent 的 GRPO——大量采样 → 评分 → 策略梯度更新 Agent 决策 | ★★★★★ |

### 3.6 Painter Profile & Archive（画师档案与存档）

画师是系统的**一等实体**，不是某次运行的产物。一个画师实例由五部分组成，合起来才构成「这个画师是谁」：

- **身份**：painter_id、名称、创建时间、谱系（派生自哪个画师）
- **配置**：Agent 大脑、生图后端、参数、风格偏好
- **课程**：自己的 Curriculum Spec + 当前进度
- **记忆**：结构化经验条目与蒸馏出的规则
- **作品**：Gallery 中的图像、元数据与进化链

**存档粒度**：同一套存档结构支持两种模式，导出时一个 flag 切换——

```bash
# 完整打包：作品与记忆随包带走，导入后独立运行
paintai export painter_wu --granularity full --out painter_wu.full.paintai

# 只存配置与进度指针：作品与记忆留在原环境
paintai export painter_wu --granularity pointer --out painter_wu.ptr.paintai

# 导入：full 解包为新实例；pointer 建立外部引用
paintai import painter_wu.full.paintai --as painter_wu_copy
paintai import painter_wu.ptr.paintai --as painter_wu_shadow
```

| 模式 | 打包内容 | 作品与记忆 | 独立性 | 典型用途 |
|-|-|-|-|-|
| **full** | 配置 + 课程 Spec + 进度 + 经验记忆 + 全部作品图片 | 随包带走 | 导入即独立运行 | 迁移、分享、备份、派生 |
| **pointer** | 配置 + 课程 Spec + 进度指针 + 作品/记忆的外部引用 | 留在原环境 | 依赖原环境可达 | 同环境多实例、轻量分发、恢复 |

**导入语义**：full 导入得到的是**副本**（此后两边各自演进，互不影响）；pointer 导入得到的是**引用**（两个实例看到的是同一批作品与记忆）。pointer 指向的源环境不可达时，实例进入「断链」状态，作品区显式标记为 missing，而不是静默丢图。

**派生（fork）**：从任一存档派生新画师，可分别选择「继承进度 / 重置进度」与「继承记忆 / 清空记忆」——派生出的新画师可以顺便换一份课程路径，出身相同但成长方向不同。

**格式与版本**：存档与课程 Spec 都带 schema_version，导入时做版本迁移；旧存档升级后仍可导入，避免格式演进把历史画师锁死。

## 四、数据流设计

### 4.1 单次创作流程

```
用户/课程 → 主题描述
     │
     ▼
[Perceive] → 解构主题 → 识别所需技法/风格/参考类型
     │
     ▼
[Compose]  → 检索参考（外部 web + 内部 Gallery）
           → 检索经验（Memory 中相似场景的教训）
           → 规划构图
           → 生成 Prompt-Reference Program
     │
     ▼
[Execute]  → 调用 Generator 生图
           → 生成后自检（可选）
           → 不满意 → 修改 → 重新生成（最多 N 轮）
     │
     ▼
[Critic]   → 多维度评分
           → 生成改进建议
           → 写入 Gallery
     │
     ▼
[Learn]    → 对比成功/失败轨迹
           → 蒸馏经验 → 写入 Memory
           → 更新课程进度
```

### 4.2 课程推进流程

```text
课程规格（Spec）→ 当前阶段/关卡（由本画师自己的课程决定）
     │
     ▼
生成训练任务（主题 + 约束 + 本关卡 skill 目标）
     │
     ▼
单次创作流程（4.1）× K 个任务
     │
     ▼
关卡评估 → K 个作品的平均分 > 阈值？
     │
     ├── YES → 解锁下一关 → 检查是否完成阶段
     │                              │
     │                              ├── YES → 阶段结业 → 下一阶段
     │                              └── NO  → 继续当前阶段
     │
     └── NO  → 针对弱项生成补充练习 → 回到创作流程
```

## 八、关键设计决策与取舍

### 8.1 为什么不直接用 GenEvolve/GenAgent 这类现成框架？

它们聚焦于「单次生图的质量最优」，而 Paintai 的核心差异在于：

- **纵向维度**：同一主题反复画，每次更好——这是 GenEvolve 不关心的
- **课程结构**：从基础到高级的系统学习路径——它们没有
- **可观测的成长**：用户能看到成长轨迹，不是黑盒优化

**但可以借鉴其组件**：VED 经验蒸馏、GRPO 策略优化、Prompt-Reference Program 等都可以按需引入。

### 8.2 Agent 大脑选 VLM 还是纯 LLM？

选 VLM。因为画师需要「看」——看参考图、看自己的作品、看 Critic 反馈截图。纯 LLM 只能用文本替代品，丢失大量视觉信息。

### 8.3 生图后端为什么不全用开源？

开源模型（SDXL/Flux）可以本地部署做风格化/微调，但闭源 API（DALL·E 3）在基础质量上更稳定。双后端策略：DALL·E 做质量基线，SDXL 做风格实验和 LoRA 微调。

### 8.4 经验蒸馏真的要做吗？MVP 会不会太重？

MVP 不做完整的 VED。Phase 0-2 用简化版：创作后将 Critic 反馈 + 成对比较结果存入结构化 Memory，下次相似场景检索并注入。完整 VED（token 级蒸馏）放到 Phase 3+。

### 8.5 课程为什么必须可自定义？

把 6 阶段模板写死，「画师是被生成出来的」这件事就失去了大半意义：所有画师都从同一个 L1 起步，成长曲线形状雷同，用户定制不出「专攻水墨」「速成写实」这类差异化的画师。放开这条约束之后：

- **模板降级为默认值**：内置模板只是「不指定时的默认路径」，自定义 Spec 与它平权
- **画师可以按目标生成**：给定目标（风格专精 / 考试冲刺 / 自由探索），Agent 可直接生成对应 Spec，画师的「出身」因此可以不同
- **派生画师可以换课**：派生时保留身份与记忆，替换课程路径

代价是引擎不能再假定阶段数与顺序，所有进度记录必须挂在稳定的 stage_id / lesson_id 上而不是序号——这是 v1.1 把进度锚点改成 ID 的原因。

### 8.6 存档粒度：full 与 pointer 怎么选？

两者不是「完整版 vs 简版」的优劣关系，而是两种用途：

| 维度 | full | pointer | 取舍 |
|-|-|-|-|
| **体积** | 随作品与记忆数量线性增长 | 恒定（只有配置 + 指针） | 作品多了以后差距很明显 |
| **独立性** | 导入即独立运行，不依赖原环境 | 依赖原环境可达 | pointer 不适合交付给他人 |
| **可分享性** | 可以直接发给别人 | 不能独立分享 | 分享场景只能 full |
| **典型场景** | 迁移、分享、备份、派生 | 同环境多实例、轻量分发、恢复 | 两者可组合使用 |

导出时一个 flag 切换：`export --granularity full|pointer`。选择原则：**要让画师离开这台机器，就用 full；只是换个名字、换台机器接着画、或者想在同一环境里同时开多个实例，就用 pointer**。

## 九、实施决策与待解决问题

1. **交付方式（已确定）**：代码通过当前 Git 凭据提交到 GitHub 仓库；模型权重、运行数据和本地密钥配置不入库。
2. **MVP 技术栈（已实施）**：Python 业务层与 FastAPI 后端，React + TypeScript 前端。构思、生图、评价分别配置可替换 provider；当前已验证 Qwen2.5、SD-Turbo 和 Qwen3-VL 的全本地闭环。
3. **交互入口（已实施）**：CLI 与独立网页画室共用业务层，网页通过 HTTP API 提交后台任务；开发与接口约定见 [WEB.md](WEB.md)。
4. **默认课程模板的关卡设计**：内置模板仍建议你定方向与粒度——但已不阻塞推进，因为任何画师都可以先用自己的 Spec 起步
5. **存档格式的对外交换方式**：是否需要公开 schema、签名校验，以及跨版本迁移要承诺到什么程度？内部自用与开放分享的要求不同
6. **pointer 跨环境引用的稳定性**：用 URI 寻址还是内容寻址？源环境长期不可达时，「断链」状态是否需要额外的离线兜底
